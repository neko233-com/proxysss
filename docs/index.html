Beginner path

快速开始

这不是“先背概念再动手”的文档。你应该先有一个能工作的配置，然后再知道为什么它工作。

5 分钟可用

第一个反向代理

你只有一个站点，要把 app.example.com 代理到本机 9000 端口。

http:
  plain_bind: 0.0.0.0:80

services:
  reverse_proxy:
    routes:
      - name: app
        match:
          hosts: ["app.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://127.0.0.1:9000"
正式上线

只填域名就给 WebSocket 加 WSS

A/AAAA 指向网关且公网 443 可达时，只填写域名即可通过默认 TLS-ALPN-01 + ECDSA P-256 免费签正式证书；不需要证书脚本、DNS API 或邮箱。极老旧客户端可选 RSA-2048；HTTP-01 仍可显式启用。

http:
  plain_bind: 0.0.0.0:80
  tls_bind: 0.0.0.0:443
  tls:
    auto_https:
      domains: [wss.example.com]

常用配置示例

Static + API

官网静态站点 + API 反向代理

官网直接从磁盘分发，HTML/CSS/JS/图片/字体/音视频支持缓存、大文件流式发送和 Range 断点续传；API 单独走后端服务，便于缓存和排障。

services:
  static_sites:
    - name: homepage
      hosts: ["www.example.com"]
      root_dir: "./www"
      index_files: ["index.html"]

  reverse_proxy:
    routes:
      - name: api
        match:
          hosts: ["api.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://127.0.0.1:8080"

AI / SSE

给 LLM 流式输出做网关

面向 OpenAI-compatible / New API / SSE 长响应，强调小包 flush 和无副作用性能优化。

runtime:
  performance:
    enabled: true
    traffic_profile: small

services:
  ai_proxy:
    routes:
      - name: llm-edge
        match:
          hosts: ["ai.example.com"]
          path_prefix: "/v1"
        upstreams:
          - url: "https://api.openai.com"
        transport:
          flush_interval_ms: 0
          tcp_nodelay: true
Weighted cluster

权重 + 健康检查 + 缓存 + 限流

给正式 API 集群用的骨架，不是演示配置。适合上线前进一步叠加观察和压测。

services:
  reverse_proxy:
    routes:
      - name: api-cluster
        match:
          hosts: ["api.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://10.0.0.11:8080"
            weight: 3
          - url: "http://10.0.0.12:8080"
            weight: 2
        load_balance:
          strategy: weighted_round_robin
          active_health:
            path: "/healthz"
            interval_secs: 5
            timeout_ms: 1200
Game / Realtime

游戏 TCP、UDP、KCP、QCP

HTTP 以外的边缘网关能力也要明确可配，不需要把实时服务硬塞进反向代理语义里。

tcp:
  listeners:
    - name: game-tcp
      bind: 0.0.0.0:7000
      nodelay: true
      routes:
        - name: zone-a
          upstreams:
            - addr: "10.0.1.10:7000"

udp:
  listeners:
    - name: game-udp
      bind: 0.0.0.0:7001
      session_ttl_secs: 45
      max_associations: 150000
MQTT / IoT

MQTT TCP、MQTT over WebSocket、CoAP-style UDP

proxysss 是设备和 broker 前面的边缘网关，不是假装自己是 broker。

services:
  reverse_proxy:
    routes:
      - name: mqtt-ws
        match:
          hosts: ["iot.example.com"]
          path_prefix: "/mqtt"
        upstreams:
          - url: "http://127.0.0.1:8083"

tcp:
  listeners:
    - name: mqtt-tcp
      bind: 0.0.0.0:1883
Wildcard TLS

泛域名证书 + DNS-01

做 *.example.com 或多节点证书管理时，直接走内建 acme_managed 的 DNS provider 工厂。

http:
  tls:
    mode: acme_managed
    acme:
      enabled: true
      email: "ops@example.com"
      challenge: dns01
      key_algorithm: ecdsa_p256
      dns:
        provider: cloudflare
        credentials:
          api_token: "REDACTED"
Expert path

进阶配置与能力边界

这张表不是营销词汇表，而是“应该配到哪里”的决策速查。

配置面 适合什么 不要拿来做什么
services.reverse_proxy.routes普通 HTTP / API / WebSocket / SSE 大多数网站、后台、流式 API 都从这里开始。 不要用它去伪装 TCP / UDP 原生协议。
services.ai_proxyOpenAI-compatible / New API 需要更明确的 AI 网关语义、上游池、SSE 传输策略。 不要把所有 HTTP 都硬塞进 AI proxy。
services.domain_routes站点级编排 按域名把静态、API、WebDAV 等能力拼成一个站点。 不要把它当成唯一实际执行面。
services.static_sites静态资源 / CDN 回源 HTML、CSS、JS、图片、字体、音视频、大文件下载、Range 断点续传。 不要把业务鉴权写进静态文件层，复杂策略放脚本或上游。
services.service_discoveryConsul / etcd / Nacos 把注册中心服务映射到 HTTP、TCP、UDP 上游池的控制面声明。 不要让每个热路径请求临时查注册中心。
tcp.listenersTCP 原生流量 数据库、游戏长连接、MQTT TCP、TLS passthrough/SNI 场景。 不要期待 HTTP 头级别策略。
udp.listenersUDP、KCP、QCP、CoAP-style 实时设备、游戏、会话型 UDP 网关。 不要把它包装成应用终端本身。
Operations

检查运行状态与排查问题

下面这些命令都是给人和 agent 都能快速看懂的，不需要翻 YAML 原文猜最终效果。

proxysss config explain
proxysss config capabilities
proxysss config watched-scripts
proxysss config routes
proxysss config reload-plan
proxysss config nginx-parity --format yaml
proxysss token show

性能相关的判断也应该按这个顺序做：先确认能力、热重载边界和 warm-up，再在本机 Docker 或原生 amd64 Docker 运行 benchmark-ubuntu24-amd64-docker.sh，由脚本硬校验 Ubuntu 24.04 x86_64 容器并把通用场景与透明 QCP 按 1x/2x/4x 一起放大；arm64 daemon 的结果明确标记为 emulated-amd64，不能冒充物理 x86。涉及公网/NIC 延迟时，再从独立 client 主机运行 benchmark-cross-host-wss.sh，由 systemd cgroup 强制 4 CPU / 300k nofile 并记录内存峰值与每连接成本后保存原始证据。GitHub Actions 只做打包，不得运行性能压测；内存上限仅在声明生产预算时设置，而不是只截一张单场景好看的图。

CDN 回源与安全目录服务

services.static_sites 支持回源令牌、TCP 对端 CIDR、短期 HMAC-SHA256 签名 URL、站点限流和缓存控制。鉴权先于文件缓存、HEAD、Range 与 304；签名资源返回 no-store。目录索引默认关闭，显式开启后支持大小、GMT 时间、安全链接和条目上限；默认隐藏点文件并检查真实路径边界。

源站令牌只鉴别 CDN，访客防盗刷和缓存命中时的授权须在 CDN 边缘执行。阅读完整配置、签名算法与幂等验证说明 →

安全开关与 Windows/macOS/Linux 适配

proxysss config security 输出安全开关、默认值和中文建议；CDN 鉴权与 FTP 策略可独立停用，保留规则。proxysss config performance 只读探测系统版本、I/O 后端和 socket 参数。Windows/macOS 保留 TCP 自动调节，并提供 keepalive、有界 UDP 缓冲；Linux 延续发行版与 CPU 自适应策略。Windows/macOS 保持现有调度，系统适配只作用于 socket；Linux 保留 CPU 自适应数据运行时。runtime.performance 在启动时固定，修改后需重启。

Docker 验证固定使用 proxysss-verify，运行前后清理同名项目容器，报告覆盖写入项目内固定目录。查看完整配置、安全建议和验证边界

管理后台与内置文档

默认在 http://127.0.0.1:7777/ 查看运行状态。后台使用中文导航、表格与表单，原始 JSON 位于可折叠的诊断区。配置写入和配置展示默认关闭。管理监听器与公共监听器均提供 /docs.html；文档模板、样式和交互脚本嵌入单个二进制。

Windows 使用隐藏启动器注册登录自启动。英文与中文安装说明分别位于仓库的 README.md 和 README-CN.md；详细配置见配置指南。
