v1.3.16 独立双容器 2C2G 复测、调度回退与发布资产收缩

2026-11-22 用户否决单机 loopback 和 Windows host client，要求用 Docker 模拟两台独立 Linux 2C2G 机器：一台服务器、一台客户端，经 bridge 网络做真实 HTTP/1.1 keep-alive 对照。v1.3.15 的每核 pinned 四队列在该环境下被推翻；本版改为共享 Tokio runtime + 两个 SO_REUSEPORT 队列，并把发布资产从 8 个收缩到 5 个。

双容器环境

  • 服务器容器 nginx:1.28，--cpus=2 --memory=2g；后端 nginx 与候选网关同容器，网关 19080、后端 19081，不发布宿主端口。
  • 客户端容器 debian:bookworm-slim，2 CPU / 2 GiB；Go HTTP/1.1 负载器，64 条预连接。
  • 网络为 Docker bridge proxysss-bench-two-host；同一轮只启动一个候选网关。
  • 服务器/客户端实测 cpu.max=200000 100000、memory.max=2147483648；2 秒预热 + 5 秒测量，3 轮交替，每请求校验状态与正文长度。

为什么撤回 pinned 四队列

v1.3.15 的同机 loopback 结论是双核 small 使用每核 pinned 单线程 runtime + 四个 SO_REUSEPORT 队列，1 KiB 静态 1.098x。独立双容器复测显示同一配置只有 0.851x / 1.024x / 1.214x。根因不是静态 sendfile，而是 64 条长连接在 SO_REUSEPORT 上的放置偏斜：pinned shard 无法把 ready 任务迁到空闲核，单核被压满，另一核空闲。

配置static-1kstatic-64kproxy-1k

同二进制 bulk 共享 runtime1.307x1.250x2.082x

共享 runtime + 两队列（采用）1.114x1.370x1.686x
最终正式三轮1.197x1.230x2.014x

代码上仅 balanced 保留每核独立 runtime；small 与 bulk 在 2 核也使用共享 runtime。plain_http_accept_worker_count_for 删除 small && cores == 2 固定返回 4 的分支，2 核统一为 2 个 SO_REUSEPORT 队列。32 KiB 静态分界、同步 sendfile、fd 池、版本锚点和 EAGAIN 背压不变。

发布资产收缩为 5 个

8 个资产不是 8 个 Linux 发行版，而是 6 个 Rust 目标 + 2 个 Windows MSI。本版收缩为：Linux amd64、Linux arm64、macOS arm64、Windows amd64 ZIP、Windows amd64 MSI。

  • proxysss-linux-amd64.tar.gz / proxysss-linux-arm64.tar.gz：完全静态 musl，跨 glibc 发行版通用；x86_64 与 aarch64 是不同 CPU 架构，不能合并成一个二进制。
  • proxysss-darwin-arm64.tar.gz：Apple Silicon；Intel Mac 需要时从源码构建。
  • proxysss-windows-amd64.zip / .msi：Windows x86_64 便携包和当前用户安装包；Windows ARM64 需要时从源码构建。

移除 macOS Intel 与 Windows ARM64 是为了减少每次发版的 CI 目标和用户下载选择；不是移除源码支持。Linux 仍不按发行版分别发版，静态 musl 已解决发行版兼容。

发布包可移植性

  • Linux 打包硬检查 readelf -d 无 NEEDED、readelf -l 无 INTERP、file 为 statically linked / static-pie linked。
  • 同一 x86_64 最终二进制在 Debian 12、Ubuntu 24.04.3 LTS、Rocky Linux 9.9、AlmaLinux 9.9、Alpine 3.21 rootfs 启动，并通过 HTTP、HEAD、Range 206/100 字节、HTTPS HTTP/2 与管理 healthz。
  • Windows 使用 -C target-feature=+crt-static，dumpbin /dependents 拒绝 VCRUNTIME*、MSVCP*、ucrtbase.dll、api-ms-win-crt-*；CI、deploy、release 使用同一 rustflags。
  • Windows ZIP 使用系统 tar.exe（bsdtar），同一完整文档包 9,119,155 B / 0.75s，对比 Compress-Archive 9,415,196 B / 1.43s。

测试与边界

  • Windows 本机 cargo test --locked：425 passed / 0 failed（VS2022 BuildTools 14.44 + Windows SDK 10.0.26100）；Linux cargo test --locked --target x86_64-unknown-linux-musl：454 passed / 0 failed（WSL Alpine 3.24，rustc 1.100.0，本版最终代码实测）；cargo fmt --check 通过。最终 Linux 二进制 SHA-256 0a1e51e768bda76f315a61218a03bfc02abba71eb1a1846e139df3db4d8612df，23,494,288 B，static-pie、无 NEEDED / INTERP。
  • 发布工作流只打包，不跑性能基准；tag 前必须匹配 Cargo.toml 版本与 CHANGELOG.md 的 ## v1.3.16。
  • 双容器结果只覆盖 static-1k、static-64k、proxy-1k 三个 HTTP/1.1 场景，不是物理双机、真实网卡、TLS/H2、WebSocket、TCP、UDP 或全协议混合负载证据。
  • 5 个资产是发布矩阵，不表示只支持这些平台源码构建。
