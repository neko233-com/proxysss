proxysss 使用文档

从 Caddy 迁移到 proxysss。

将 Caddyfile 中的站点、反向代理、静态文件和自动 HTTPS 配置迁移到 proxysss。下面提供对应示例，并说明证书申请、脚本扩展和部署验证的差异。

先迁最常见场景 再看高级迁移 回 docs 首页
Migration mindset

先理解 Caddy 和 proxysss 的思路差别

Caddy 的强项是上手快和自动 HTTPS；proxysss 的目标是把 nginx 级网关能力放进一套更容易维护的单文件 YAML。没有用户路由命中 / 时，proxysss 才返回只含 GitHub 和 GitHub Docs 的内建欢迎页；业务首页应显式声明 static site/route。

Caddy 思路 proxysss 落点 适合什么
reverse_proxy services.reverse_proxy.routes 普通站点反代
handle_path /api/* match.path_prefix + strip_prefix API 前缀改写
file_server services.static_sites 静态站点
自动 HTTPS http.tls.mode: acme_managed 默认推荐
layer4 场景 tcp.listeners / udp.listeners 原生 TCP / UDP
Beginner path

先迁最常见的站点代理

这些例子适合从 Caddy 最常见的使用方式平滑切过来。

Whole site

整站反代

services:
  reverse_proxy:
    routes:
      - name: app
        match:
          hosts: ["app.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://127.0.0.1:9000"
API path

handle_path /api/*

services:
  reverse_proxy:
    routes:
      - name: api
        match:
          hosts: ["app.example.com"]
          path_prefix: "/api"
        strip_prefix: true
        upstreams:
          - url: "http://127.0.0.1:8080"
Static site

file_server

services:
  static_sites:
    - name: homepage
      hosts: ["www.example.com"]
      root_dir: "/srv/www"
      index_files: ["index.html"]
Auto HTTPS

自动 HTTPS / WSS

http:
  plain_bind: 0.0.0.0:80
  tls_bind: 0.0.0.0:443
  tls:
    auto_https:
      domains: [wss.example.com]

只给域名即可免费走内建 managed ACME 的正式 TLS-ALPN-01 与默认 ECDSA P-256，无需 certbot、acme.sh、DNS API 或邮箱。A/AAAA 必须指向网关，且公网 443 可达；极老旧客户端可设 http.tls.acme.key_algorithm: rsa2048。旧的显式 HTTP-01（需 80）/ TLS-ALPN-01 / DNS-01 配置保持兼容。

Advanced path

从站点代理走向完整网关

这是 Caddy 用户最容易低估的一步：proxysss 不是另一个语法不同的 Caddyfile，而是更完整的网关面。

Load balance

负载均衡 + health

upstreams:
  - url: "http://10.0.0.11:8080"
    weight: 3
  - url: "http://10.0.0.12:8080"
    weight: 2
load_balance:
  strategy: weighted_round_robin
  active_health:
    path: "/healthz"
    interval_secs: 5
    timeout_ms: 1200
AI / SSE

流式 AI 代理

runtime:
  performance:
    enabled: true
    traffic_profile: small

services:
  ai_proxy:
    routes:
      - name: llm-edge
        transport:
          flush_interval_ms: 0
          tcp_nodelay: true
TCP / UDP

layer4 迁移

tcp:
  listeners:
    - name: mqtt-tcp
      bind: 0.0.0.0:1883

udp:
  listeners:
    - name: coap
      bind: 0.0.0.0:5683
      session_ttl_secs: 30

WebDAV

文件协作入口

services:
  webdav:

      hosts: ["dav.example.com"]

      read_only: false
Validation

迁移完成的标准，要看 mixed-load

proxysss 的迁移和后续性能优化，不能只看单站点 HTTP。generic SSE、static、HTTP reverse proxy、TCP、UDP 要一起看，而且必须无副作用；KCP/QCP 是独立能力，不进入当前性能 benchmark 矩阵。涉及公网/NIC 延迟时，必须从独立 client 主机运行 scripts/benchmark-cross-host-wss.sh，Docker cpuset 数据不能冒充跨机结果。

proxysss tune linux --apply
proxysss config explain
proxysss config capabilities
proxysss config reload-plan
scripts/benchmark-ubuntu24-amd64-docker.sh

默认 GitHub Actions CI 只负责全平台二进制打包，禁止任何性能压测 workflow；迁移后的性能判断在本机或原生 Docker 跑上面的 Ubuntu 24 amd64 mixed-load，模拟结果不冒充物理 x86。v1.3.5 UDP fast path 当前专项结果是 udp-stream 4.045x。

CDN 回源与安全目录服务

services.static_sites 支持回源令牌、TCP 对端 CIDR、短期 HMAC-SHA256 签名 URL、站点限流和缓存控制。鉴权先于文件缓存、HEAD、Range 与 304；签名资源返回 no-store。目录索引默认关闭，显式开启后支持大小、GMT 时间、安全链接和条目上限；默认隐藏点文件并检查真实路径边界。

源站令牌只鉴别 CDN，访客防盗刷和缓存命中时的授权须在 CDN 边缘执行。阅读完整配置、签名算法与幂等验证说明 →

安全开关与 Windows/macOS/Linux 适配

proxysss config security 输出安全开关、默认值和中文建议；CDN 鉴权与 FTP 策略可独立停用，保留规则。proxysss config performance 只读探测系统版本、I/O 后端和 socket 参数。Windows/macOS 保留 TCP 自动调节，并提供 keepalive、有界 UDP 缓冲；Linux 延续发行版与 CPU 自适应策略。Windows/macOS 保持现有调度，系统适配只作用于 socket；Linux 保留 CPU 自适应数据运行时。runtime.performance 在启动时固定，修改后需重启。

Docker 验证固定使用 proxysss-verify，运行前后清理同名项目容器，报告覆盖写入项目内固定目录。查看完整配置、安全建议和验证边界

管理后台与内置文档

默认在 http://127.0.0.1:7777/ 查看运行状态。后台使用中文导航、表格与表单，原始 JSON 位于可折叠的诊断区。配置写入和配置展示默认关闭。管理监听器与公共监听器均提供 /docs.html；文档模板、样式和交互脚本嵌入单个二进制。

Windows 使用隐藏启动器注册登录自启动。英文与中文安装说明分别位于仓库的 README.md 和 README-CN.md；详细配置见配置指南。

迁移原则： 先迁最简单的 reverse_proxy，再拆 static_sites、ai_proxy、tcp.listeners、udp.listeners，最后补 TLS、health、cache 和 benchmark。这样最容易看清能力边界，也最容易发现副作用。
