proxysss architecture / human-readable

读架构不是为了崇拜内部实现，而是为了知道请求会怎么走。

这页把 proxysss 的架构拆成“你现在需要知道什么”。新手应该先知道 listener、route、policy、upstream 的顺序；高手应该快速确认脚本 hook 放在哪里、哪些东西能热重载、哪些优化必须按 mixed-load 证明无副作用。

Mental model

先记住 5 个角色，架构就不会看乱。

proxysss 不想把所有东西都折叠成“神秘代理黑盒”。它把每个责任面尽量拆开，而且名字要像人在排障时会说的话。

1

Listener

先接住流量。HTTP / HTTPS / H2 / H3、TCP、UDP、FTP 都有自己的监听入口。

2

Route surface

决定这条流量落到哪个能力面：`reverse_proxy`、`ai_proxy`、`static_sites`、`webdav`、`tcp.listeners`、`udp.listeners`。

3

Policy chain

限流、缓存、压缩、访问控制、健康检查都在这里影响行为，但不应该把数据路径锁死成低性能结构。

4

Extension hooks

TypeScript 只在该出现的地方出现：HTTP 的 `access` / `balancer`，以及 stream 的 `preread` / `log`。

5

Runtime operations

配置加载、warm-up、健康状态、token、热重载边界、watchdog、metrics 一起构成真正能运维的网关。

Listener HTTP / TCP / UDP / FTP 先接流量
→
Route surface 域名、路径、SNI、listener 名称决定能力面
→
Policy chain 缓存、限流、健康检查、压缩、ACL
Extension hooks 只在需要业务感知时介入
→
Upstream / file / service 进入上游池、静态文件、WebDAV 或内建服务
→
Logs / metrics / health 观测、告警、验证、自动化接口
HTTP flow

一条 HTTP 请求怎么走

这是大多数人最先要理解的路径，因为它串起了反向代理、AI SSE、静态站点和脚本扩展。

Step 1

进入 HTTP listener

请求先到 `http.plain_bind` 或 `http.tls_bind`。TLS、HTTP2、HTTP3 是否参与，在这里决定。

Step 2

按 host / path 命中能力面

此时会决定它属于 `reverse_proxy.routes`、`ai_proxy.routes`、`static_sites` 还是 `webdav`。

Step 3

应用策略链

限流、缓存、访问控制、响应策略、主动健康检查等在这里影响行为。

Step 4

必要时进入 TS hook

只有当 YAML 表达不了业务决策时，`access` / `balancer` 才应该介入。

Step 5

发往上游或本地能力面

最终不是去上游池，就是读静态文件、走 WebDAV、返回内建服务结果；没有用户路由命中 `/` 时才返回只含 GitHub 与 GitHub Docs 的零外部资源欢迎页。静态文件支持 Range/206 断点续传，大文件区间会流式发送。

http:
  plain_bind: 0.0.0.0:80
  tls_bind: 0.0.0.0:443

services:
  reverse_proxy:
    routes:
      - name: app
        match:
          hosts: ["app.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://127.0.0.1:9000"

这份最小配置对应的架构路径很直白：`TLS/HTTP listener -> reverse_proxy route match -> upstream connect -> access/error log`。

普通公网 WSS 可把 `http.tls.auto_https.domains` 直接写成域名列表：非空列表会选中免费的内建 managed ACME、正式 Let's Encrypt、默认 TLS-ALPN-01 与 ECDSA P-256 证书密钥。临时 `acme-tls/1` 证书、证书持久化、续期和 reload 都由网关处理，不需要外部证书工具、DNS API 或账号邮箱；A/AAAA 必须指向网关且公网 443 可达。极老旧客户端可用 `http.tls.acme.key_algorithm: rsa2048`；显式 HTTP-01（需 80）、TLS-ALPN-01、DNS-01 与外部 ACME 配置仍兼容。

Stream flow

一条 TCP / UDP 流量怎么走

这里是 proxysss 和“只会讲 HTTP 的文档”最不一样的地方。实时流量不是附属功能，而是一等公民。

TCP

TCP listener

按 listener 名称、SNI、直通规则决定流量去哪里。典型场景是数据库、MQTT TCP、游戏长连接。

UDP

UDP listener

重点不只是转发，还有 `session_ttl_secs` 和 `max_associations` 这类会话治理；KCP 和 QCP 是独立 listener，协议帧都留给各自上游服务。

Hook

`preread` 只做前置选路

如果你真要做 player_id / device 亲和，脚本应该只负责快速决定 upstream，不要把慢逻辑塞进热路径。

tcp:
  listeners:
    - name: game-tcp
      bind: 0.0.0.0:7000
      nodelay: true
      connect_timeout_ms: 1500
      routes:
        - name: zone-a
          upstreams:
            - addr: "10.0.1.10:7000"

udp:
  listeners:
    - name: game-udp
      bind: 0.0.0.0:7001
      protocol: qcp
      session_ttl_secs: 45
      max_associations: 150000
      routes:
        - name: zone-a-udp
          upstreams:
            - addr: "10.0.1.10:7001"

Linux 性能模式从 cgroup effective cpuset 发现完整 CPU 集，再建立全核 `SO_REUSEPORT` listener fanout；每个 listener 同时设置对应 `SO_INCOMING_CPU`，让 flow steering、accept owner 与 pinned data worker 保持同核。默认 small 把 HTTP/1.1、HTTP/2/TLS、WebSocket、TCP、UDP 与透明 QCP 放进一个 CPU-sized Tokio runtime；balanced 将每个 plain HTTP accept loop 固定到独立单线程 Tokio runtime，消除跨核 work stealing 和共享 LIFO slot 引起的尾延迟。plain runtime 每 8 次 task poll 检查 I/O，shared-small 保持 16 次。balanced 的 TLS/H2 使用 nice 5 bounded runtime；UDP/QCP 使用 `ceil(cpuset/2)` nice 3 runtime；policy-free realtime TCP 与 plain WebSocket 在 connect/upgrade 后进入 `ceil(cpuset/2)` nice 3 native epoll relay。nice 5 realtime 实验降低吞吐且未改善 static-large，已回退。8 MiB 以上 balanced 静态对象由连接所属 HTTP owner 直接 sendfile；warm-up 校验目标并为每个热大文件注入有界 lock-free descriptor pool。并发响应独占 file description，完成后归还；池满时 surplus descriptor 自动关闭，避免共享 `struct file`、per-response synchronous open jitter 和无界 idle FD retention。partial sendfile 进度保留在同一次 readiness 操作内，`EAGAIN` 会清除过期 writable 状态，但不会丢失已发送字节或触发下一次必然失败的 syscall。大文件连接强制深发送队列的实验把 1×/2× static-large 降到 nginx 的 0.891-0.896x，并恶化 WebSocket/static 尾延迟，已删除。全核 balanced sendfile reactor 虽能稳定单项 static-large，但在 4× 混合矩阵造成 QCP 错误和跨协议 p95/p99 回退，故仅 bulk profile 可启用。`ceil(cpuset/4)` nice 0 的 stream 实验把 1×/4× TCP/WebSocket 压到 0.85-0.98x nginx 且恶化 p95/p99，已拒绝。统一 balanced TLS 的实测会产生 16-21 ms 跨协议尾峰，并把 HTTPS saturation 压到最低 0.225x。global injection queue 每 31 次 poll 检查。plain static 采用低密度 256 / 高密度 128 响应 fairness boundary；raw reverse/SSE 依靠有界 upstream/downstream readiness。balanced 专用 UDP 依靠 Tokio socket scheduling；shared-small UDP 保留 4 包边界。静态文件采用 2 秒 freshness window，并在单独 nice-10 control runtime 重验证 metadata/body；freshness timestamp 与 in-flight claim 使用共享原子状态，stale reader 不获取 DashMap 写锁，metadata 未变化时不重建 H2 snapshot。small-profile WebSocket 使用 readiness-bounded 64-poll normal relay turn。

每次 level-triggered readiness 最多连续 drain 8 个 16 KiB read batch，合并已排队 WebSocket/game/TCP 小帧的 epoll/hash dispatch；达到上限就归还 event loop，partial write 立即进入显式 pending/backpressure。owner 只有在 `epoll_wait` 确实阻塞过、且每 worker 不超过 32 对连接时才追加一次 nonblocking reply poll，用于接住 fixed-rate tick 的即时回包；持续 ready 的 saturation 不启用该 spin。普通数据事件只在本端已经观察到 EOF 后才做完整 pair-finished 查询，去掉每帧两端状态查找。

Linux 性能模式下 UDP 使用全核 CPU 自适应 `SO_REUSEPORT` socket fanout 并复用有界 UDP buffer pool；默认 small 的 recv loop、association reader 留在共享 CPU-sized data runtime，balanced 则进入 `ceil(cpuset/2)` nice 3 专用 UDP runtime。无 policy worker 本地缓存 upstream/config 快照；pending 去重使用分片集合，association prune 按时间、创建数量和容量压力节流。

Hooks and plugins

脚本应该放在哪里，不应该替代什么

proxysss 的产品方向很明确：它是通用网关，脚本是扩展点，不是把基础能力重新写一遍的借口。

Hook 适合做什么 不该做什么
access HTTP 路由阶段做小范围业务决策、path 改写、header 注入。 不要拿来重写整个基础反向代理面。
balancer 在已有路由基础上改 upstream、灰度、亲和。 不要在这里做慢逻辑或大量序列化。
preread 给 TCP / UDP 做前置选路。 不要把实时热路径变成脚本业务 worker。
log 观测、计数、轻量记录。 不要做阻塞或高成本计算。 
script:
  args:
    - "./gateway.ts"

plugins:
  auto_load_dir: "./plugins"

这两条配置说明的是“脚本从哪里来”，不是“把所有能力都交给脚本”。固定网关能力优先用 YAML，本体能力缺口再推动 Rust / YAML 面完善。

Reload boundaries

哪些东西能热重载，哪些一定要重启

这是架构页必须讲明白的运维边界，否则文档再漂亮也不适合真实生产。

可以热重载 需要重启
配置值和脚本 `proxysss.yaml`、主脚本、自动加载插件脚本、大部分合并后的配置值 Listener 身份 `http.plain_bind`、`http.tls_bind`、`http.h3_bind`、TCP/UDP bind 集合
路由面 `services.reverse_proxy.routes`、`services.service_discovery`、`static_sites`、`webdav`、FTP upstream 管理面与 TLS 关键边界 `admin.bind`、`http.tls.mode`
Warm-up 会重跑 注册中心映射读取、热文件缓存、sendfile 准备、上游 keepalive 预拨、`/healthz` warm 状态 日志核心设置 日志路径、日志级别等核心输出边界
Performance discipline

性能不是单链路冲分，而是全局无副作用优化

这是 proxysss 架构设计里非常核心的一条线：热路径避免全局锁、尽量使用分片或原子结构、静态和流式都要参与 warm-up、结论必须靠 mixed-load 压测证明。

Hot path

不要让控制面锁卡住数据面

热路径优先 per-connection、per-listener、per-worker 分片和池化；全局锁只留给配置、证书、控制面协作。

Warm-up

配置加载后先自我预热

静态热文件、sendfile 描述符、小对象完整 HTTP/1 keep-alive 响应 bytes、反向代理 keepalive 池都会先准备好。每个去重 upstream pool 只预拨一对 socket，避免从启动 runtime 大批创建后跨 reactor 长期使用；数字 IP 在 pool 创建时预解析为 SocketAddr。

Validation

只赢一项，不算赢

generic SSE、静态、HTTP reverse proxy、WebSocket、TCP、UDP 与透明 QCP 都要一起看；角色隔离脚本默认在每个 1×/2×/4× 尺度运行 1 次 saturation 和 2 次反向 candidate order 的 equal-load 1 秒样本，共 18 秒 active client measurement，并硬限制在 20 秒内。`validation_elapsed_secs` 累加采样窗口，`validation_wall_elapsed_secs` 单独记录进程启动、结果复制和报告解析。latency report 使用两次样本 median，任一轮错误取最大值，equal-offered-load 严格判 p50/p95/p99。KCP/QCP frame termination 不拿 nginx 做伪对照；QCP 行只验证与等价 nginx UDP listener 的透明 edge forwarding。

Fast lane

默认头语义也要能吃到快路径

plain HTTP 的 raw reverse proxy 和 raw SSE fast lane 保留 `X-Forwarded-*` / `Forwarded`。Plain/TLS fast-lane request reader 直接读入 persistent per-connection BytesMut。warm-up 为小静态对象预构建完整 HTTP/1 keep-alive 响应 bytes；同一 connection 后续 exact static GET head 命中 connection response cache，一秒 revalidation clock 每 256 次 exact hit 检查一次。低密度连接每 256 响应 cooperative yield；高密度 plain HTTP 使用每 128 响应的 saturated fairness boundary。WebSocket relay 使用 64-poll normal budget。HTTP/2 使用固定大窗口与 warm-up immutable snapshot。raw reverse 复用 upstream lane、request/response buffer 与 framing cache，只有尚未收全的 body 才进入 bounded ByteBufferPool relay。

WebSocket relay

游戏重连不会反复打分配器

small 的 plain WebSocket 与 WSS 在握手后使用多核 Tokio relay；balanced 的 policy-free plain WebSocket 会交给 CPU 自适应 native epoll relay，WSS 留在有界 TLS Tokio runtime。只有出现 pending 数据时才从有界 `ByteBufferPool` 借 buffer，空闲长连接不会预占每方向固定大块内存。4c 生产参考包络默认验证 20k idle WSS 容量和最多 4096 条活跃消息连接，并分别比较握手/消息的 p50、p95、p99，记录内存 current/peak 和每连接成本；它不是任意固定 RAM 准入门槛。

Static sendfile

零拷贝也要保证并行公平

ALPN 已确认的 HTTP/2 直接进入 Hyper H2 builder。warm-up 构建 ArcSwap/FxHashMap 只读静态响应表。每条 H2 connection 使用本地 `FuturesUnordered` executor，并在每个 ready stream 完成后 cooperative yield，防止热 H2 connection 长驻 Tokio LIFO slot，阻塞同 shard 的 HTTP/1、SSE、WebSocket、TCP、UDP/QCP。过期文件继续 stale-while-revalidate 并原子替换快照。

`benchmark-ubuntu24-amd64-docker.sh` 在 Ubuntu 24.04 x86_64 容器内构建当前 checkout，并把 gateway、backend、client 固定到互不重叠的 cpuset/cgroup。HTTP、HTTPS、static-large、SSE、WebSocket、TCP、UDP 与透明 QCP 按 1×/2×/4× 同时放大；逐档判定 saturation 吞吐和 equal-load p50/p95/p99。equal-load 取较慢 saturation 的 25%，双方须完成至少 98% 可执行 target。HTTP/SSE 使用 centered uniform phase 并对 aggregate slot 四舍五入；UDP/QCP 使用保留 1 ms completion guard 的同步 whole per-connection ticks，TCP 保留 2 ms，WebSocket 为 framing 和两次用户态协议转换保留 5 ms。nginx 1.31.2 mainline 使用 `-O3 -fno-plt`、相同 gateway cpuset、sysctl 与等价协议配置。完整矩阵 active measurement 最多 20 秒；Docker role isolation 不能冒充三台物理机。

20 秒上限按 active measurement window 累加。默认每尺度运行 1 次 saturation 和 2 次反向 candidate order 的 equal-load，共 18 秒 active measurement；latency report 使用两次样本 median。inactive gateway unpause 后双方都有相同的 1000 ms excluded settle，再安排 2000 ms future start，确保 overdue timer/I/O bookkeeping 已排空，并让 4× 下 11 个发生器完成连接池与协议预热；plain HTTP/1 建立完整连接池，HTTPS/H2 预连 multiplexed session，GET/SSE 完成两次请求，每条 WebSocket/TCP/UDP/QCP 连接完成一次 echo。预热不计入 active measurement，UDP/QCP response timeout 为 500 ms。

严格矩阵中的 `protocol: qcp` 是透明 UDP edge forwarding：proxysss 与 nginx 等价 UDP listener 接受相同负载和门禁。该结果不代表 proxysss 在热路径解析或终止 QCP frame；KCP 专用封装仍不进入默认 nginx head-to-head 矩阵。
