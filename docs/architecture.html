Mental model

网关的五个组成部分

proxysss 不想把所有东西都折叠成“神秘代理黑盒”。它把每个责任面尽量拆开，而且名字要像人在排障时会说的话。

1

Listener

先接住流量。HTTP / HTTPS / H2 / H3、TCP、UDP、FTP 都有自己的监听入口。

2

Route surface

决定这条流量落到哪个能力面：reverse_proxy、ai_proxy、static_sites、webdav、tcp.listeners、udp.listeners。

3

Policy chain

限流、缓存、压缩、访问控制、健康检查都在这里影响行为，但不应该把数据路径锁死成低性能结构。

4

Extension hooks

TypeScript 只在该出现的地方出现：HTTP 的 access / balancer，以及 stream 的 preread / log。

5

Runtime operations

配置加载、warm-up、健康状态、token、热重载边界、watchdog、metrics 一起构成真正能运维的网关。

Listener HTTP / TCP / UDP / FTP 先接流量
→
Route surface 域名、路径、SNI、listener 名称决定能力面
→
Policy chain 缓存、限流、健康检查、压缩、ACL
Extension hooks 只在需要业务感知时介入
→
Upstream / file / service 进入上游池、静态文件、WebDAV 或内建服务
→
Logs / metrics / health 观测、告警、验证、自动化接口
HTTP flow

一条 HTTP 请求怎么走

配置边界：reverse_proxy.routes 用 hosts，domain_routes 用 domains，每条路由直接指向 upstream；后者不引用静态或 WebDAV 服务。static_sites 同时匹配可选 hosts 与路径；单个 webdav 按路径匹配，可通过 auth.enabled/username/password 开启 Basic 认证；认证先于路径检查和任何文件操作。查看真实配置与限制。

这是大多数人最先要理解的路径，因为它串起了反向代理、AI SSE、静态站点和脚本扩展。

Step 1

进入 HTTP listener

请求先到 http.plain_bind 或 http.tls_bind。TLS、HTTP2、HTTP3 是否参与，在这里决定。

Step 2

按 host / path 命中能力面

此时会决定它属于 reverse_proxy.routes、ai_proxy.routes、static_sites 还是 webdav。

Step 3

应用策略链

限流、缓存、访问控制、响应策略、主动健康检查等在这里影响行为。

Step 4

必要时进入 TS hook

只有当 YAML 表达不了业务决策时，access / balancer 才应该介入。

Step 5

发往上游或本地能力面

最终不是去上游池，就是读静态文件、走 WebDAV、返回内建服务结果；没有用户路由命中 / 时才返回只含 GitHub 与 GitHub Docs 的零外部资源欢迎页。静态文件支持 Range/206 断点续传，大文件区间会流式发送。

WebDAV 与 FileCloud 通过 filesystem_boundary 检查已有目标的真实路径，以及新建目标最近存在的父目录；symlink_metadata 识别悬空链接，不能用 exists 跳过。WebDAV 在阻塞任务池检查源路径、COPY/MOVE 目标和递归 COPY 的每个子项；越界、悬空链接、复制到自身/子目录及内部循环返回 403。深度优先遍历只保存当前祖先，允许有效的内部链接；删除/移动使用原始路径，避免删除链接指向的文件。PROPFIND 和 FileCloud 列表/搜索隐藏不符合边界的子项。递归 COPY 不是事务，失败后根目录内已完成的部分可能保留。

根目录及链接须由可信运维管理。这是路径检查，不是目录描述符原子沙箱；检查与打开仍有时间窗口，不保证隔离不可信本地进程的并发链接修改。该检查不进入普通反代、静态缓存或 TCP/UDP 转发路径。查看文件服务配置。

file_download 共用静态服务的条件请求与 Range 实现。WebDAV/FileCloud 完整小文件最多预读 64 KiB，大文件及多段响应按消费进度读取，每次最多 64 KiB，空闲池总计最多 8 MiB；取消或截断释放资源。HEAD 不读正文且忽略 Range。FileCloud 只允许 GET/HEAD 下载，认证下载为 private, no-store，公开可覆盖资源不自动添加 immutable；下载 URL 只解码一次，API/JSON 保留字面 + 和 %，中文文件名用 filename* 编码。

PROPFIND 支持 Depth 0/1，XML 流式输出，不积累全部目录条目；目录默认/infinity 深度返回 403 propfind-finite-depth。COPY 支持 Depth 0/infinity，MOVE 要求 infinity，Overwrite F 遇到已有目标返回 412。覆盖替换整个集合，创建返回 201、覆盖返回 204，父集合缺失返回 409。MKCOL 非空请求体返回 415，跨服务器 Destination 返回 502。锁与自定义属性必须按实际实现声明。

http:
  plain_bind: 0.0.0.0:80
  tls_bind: 0.0.0.0:443

services:
  reverse_proxy:
    routes:
      - name: app
        match:
          hosts: ["app.example.com"]
          path_prefix: "/"
        upstreams:
          - url: "http://127.0.0.1:9000"

这份最小配置对应的架构路径很直白：TLS/HTTP listener -> reverse_proxy route match -> upstream connect -> access/error log。

普通公网 WSS 可把 http.tls.auto_https.domains 直接写成域名列表：非空列表会选中免费的内建 managed ACME、正式 Let's Encrypt、默认 TLS-ALPN-01 与 ECDSA P-256 证书密钥。临时 acme-tls/1 证书、证书持久化、续期和 reload 都由网关处理，不需要外部证书工具、DNS API 或账号邮箱；A/AAAA 必须指向网关且公网 443 可达。极老旧客户端可用 http.tls.acme.key_algorithm: rsa2048；显式 HTTP-01（需 80）、TLS-ALPN-01、DNS-01 与外部 ACME 配置仍兼容。

Stream flow

一条 TCP / UDP 流量怎么走

这里是 proxysss 和“只会讲 HTTP 的文档”最不一样的地方。实时流量不是附属功能，而是一等公民。

TCP

TCP listener

按 listener 名称、SNI、直通规则决定流量去哪里。典型场景是数据库、MQTT TCP、游戏长连接。

UDP

UDP listener

重点不只是转发，还有 session_ttl_secs 和 max_associations 这类会话治理；KCP 和 QCP 是独立 listener，协议帧都留给各自上游服务。

Hook

preread 只做前置选路

如果你真要做 player_id / device 亲和，脚本应该只负责快速决定 upstream，不要把慢逻辑塞进热路径。

tcp:
  listeners:
    - name: game-tcp
      bind: 0.0.0.0:7000
      nodelay: true
      connect_timeout_ms: 1500
      routes:
        - name: zone-a
          upstreams:
            - addr: "10.0.1.10:7000"

udp:
  listeners:
    - name: game-udp
      bind: 0.0.0.0:7001
      protocol: qcp
      session_ttl_secs: 45
      max_associations: 150000
      routes:
        - name: zone-a-udp
          upstreams:
            - addr: "10.0.1.10:7001"

Linux 从 cgroup effective cpuset 发现完整 CPU 集，SO_REUSEPORT fanout 随核心数扩展。默认 small 共用每核一个 worker 的 Tokio runtime。balanced 明文 HTTP 每核独立 runtime；TLS/H2 使用 nice 5 有界运行时；UDP 使用 ceil(cores/2) nice 3 worker；无策略明文 TCP/WebSocket 每允许 CPU 一个 nice 3 soft-affinity epoll owner。真正阻塞后的请求 tick 在 1–16 对连接时探测一次，17–32 对两次，超过 32 对依赖 epoll；回复事件和持续就绪流量不额外自旋。

balanced 大于等于 8 MiB 的完整静态响应，仅在活跃传输大于数据核数且不超过每核四条时交给预热 sendfile reactor；每核不超过两条时选择均匀分布的半数 owner。独立文件描述符来自有界池，EAGAIN 保留发送进度；balanced 直接发送在非密集压力下每 2 MiB 让出 HTTP runtime，所有响应使用同一公平边界，不再按源端口或每三次响应选择是否让出；超过每核四条活跃传输时保留 16 MiB 预算并依赖 EAGAIN。reactor 的完整响应事件预算不变。静态 sendfile 不设置 SO_SNDBUF，保留 Linux 发送缓冲自动调优；写回旧数值不能清除手动设置产生的用户锁，同一 keep-alive 后续下载也会受影响。reactor 提前清除 TCP_CORK 后 owner 不重复 syscall。静态 freshness 为 2 秒，由 nice-10 控制运行时重验证。H2 每连接用 FuturesUnordered，并在每个完成流后让出。完整验证顺序见 验证指南。

balanced realtime 为每个允许 CPU 建立一个 soft-affinity native owner。每次 level-triggered readiness 最多连续 drain 8 个 16 KiB read batch，合并已排队 WebSocket/game/TCP 小帧的 epoll/hash dispatch；达到上限就归还 event loop，partial write 立即进入显式 pending/backpressure。owner 只有在 epoll_wait 确实阻塞后收到客户端请求时才追加 reply probe：不超过 16/32 对使用 1/2 次 immediate poll；超过 32 对不 spin。上游回包事件不再安排下一轮 spin，持续 ready 的 saturation 也不启用该路径。adaptive sendfile 保留 full-response event budget；active transfer 不超过每数据核 2 条时，只选择均匀分布的一半预热 owner，避免全核同时争用且不增加 epoll round，更高压力恢复全部 owner。sendfile reactor 提前清除 TCP_CORK 后把状态传回 HTTP owner，避免重复 syscall。普通数据事件只在本端已经观察到 EOF 后才做完整 pair-finished 查询，去掉每帧两端状态查找。

原生 sendfile 的完成 future 同时拥有取消责任。HTTP 等待任务退出时关闭完成通道，经每 owner 的有界无锁取消队列和 eventfd 唤醒 reactor；队列溢出才扫描已放弃作业，普通完成不扫描。清理前检查完成通道确已关闭，防止旧 fd 通知误取消复用该数字的新下载。未注册作业和连续发送轮也检查取消；已阻塞的作业无需等待客户端再次产生 I/O 即可释放 socket/file 副本。

Linux 性能模式下 UDP 使用全核 CPU 自适应 SO_REUSEPORT socket fanout 并复用有界 UDP buffer pool；默认 small 的 recv loop、association reader 留在共享 CPU-sized data runtime，balanced 则进入 ceil(cpuset/2) nice 3 专用 UDP runtime。无 policy worker 本地缓存 upstream/config 快照；pending 去重使用分片集合，association prune 按时间、创建数量和容量压力节流。

Hooks and plugins

脚本应该放在哪里，不应该替代什么

proxysss 的产品方向很明确：它是通用网关，脚本是扩展点，不是把基础能力重新写一遍的借口。

Hook 适合做什么 不该做什么
access HTTP 路由阶段做小范围业务决策、path 改写、header 注入。 不要拿来重写整个基础反向代理面。
balancer 在已有路由基础上改 upstream、灰度、亲和。 不要在这里做慢逻辑或大量序列化。
preread 给 TCP / UDP 做前置选路。 不要把实时热路径变成脚本业务 worker。
log 观测、计数、轻量记录。 不要做阻塞或高成本计算。 
script:
  args:
    - "./gateway.ts"

plugins:
  auto_load_dir: "./plugins"

这两条配置说明的是“脚本从哪里来”，不是“把所有能力都交给脚本”。固定网关能力优先用 YAML，本体能力缺口再推动 Rust / YAML 面完善。

Performance discipline

性能调度与资源分配

这是 proxysss 架构设计里非常核心的一条线：热路径避免全局锁、尽量使用分片或原子结构、静态和流式都要参与 warm-up、结论必须靠 mixed-load 压测证明。

Hot path

不要让控制面锁卡住数据面

热路径优先 per-connection、per-listener、per-worker 分片和池化；全局锁只留给配置、证书、控制面协作。

Warm-up

配置加载后先自我预热

静态热文件、sendfile 描述符、小对象完整 HTTP/1 keep-alive 响应 bytes、反向代理 keepalive 池都会先准备好。每个去重 upstream pool 只预拨一对 socket，避免从启动 runtime 大批创建后跨 reactor 长期使用；数字 IP 在 pool 创建时预解析为 SocketAddr。

Validation

只赢一项，不算赢

generic SSE、静态、HTTP reverse proxy、WebSocket、TCP、UDP 与透明 QCP 都要一起看；角色隔离脚本默认在每个 1×/2×/4× 尺度运行 1 次 saturation 和 2 次反向 candidate order 的 equal-load 1 秒样本，共 18 秒 active client measurement，并硬限制在 20 秒内。validation_elapsed_secs 累加采样窗口，validation_wall_elapsed_secs 单独记录进程启动、结果复制和报告解析。latency report 使用两次样本 median，任一轮错误取最大值，equal-offered-load 严格判 p50/p95/p99。KCP/QCP frame termination 不拿 nginx 做伪对照；QCP 行只验证与等价 nginx UDP listener 的透明 edge forwarding。

Fast lane

默认头语义也要能吃到快路径

plain HTTP 的 raw reverse proxy 和 raw SSE fast lane 保留 X-Forwarded-* / Forwarded。Plain/TLS fast-lane request reader 直接读入 persistent per-connection BytesMut。warm-up 为小静态对象预构建完整 HTTP/1 keep-alive 响应 bytes；同一 connection 后续 exact static GET head 命中 connection response cache，一秒 revalidation clock 每 256 次 exact hit 检查一次。低密度连接每 256 响应 cooperative yield；高密度 plain HTTP 使用每 128 响应的 saturated fairness boundary。WebSocket relay 使用 64-poll normal budget。HTTP/2 使用固定大窗口与 warm-up immutable snapshot。raw reverse 复用 upstream lane、request/response buffer 与 framing cache，只有尚未收全的 body 才进入 bounded ByteBufferPool relay。

WebSocket relay

游戏重连不会反复打分配器

small 的 plain WebSocket 与 WSS 在握手后使用多核 Tokio relay；balanced 的 policy-free plain WebSocket 会交给 CPU 自适应 native epoll relay，WSS 留在有界 TLS Tokio runtime。只有出现 pending 数据时才从有界 ByteBufferPool 借 buffer，空闲长连接不会预占每方向固定大块内存。4c 生产参考包络默认验证 20k idle WSS 容量和最多 4096 条活跃消息连接，并分别比较握手/消息的 p50、p95、p99，记录内存 current/peak 和每连接成本；它不是任意固定 RAM 准入门槛。

Static sendfile

零拷贝也要保证并行公平

ALPN 已确认的 HTTP/2 直接进入 Hyper H2 builder。warm-up 构建 ArcSwap/FxHashMap 只读静态响应表。每条 H2 connection 使用本地 FuturesUnordered executor，并在每个 ready stream 完成后 cooperative yield，防止热 H2 connection 长驻 Tokio LIFO slot，阻塞同 shard 的 HTTP/1、SSE、WebSocket、TCP、UDP/QCP。过期文件继续 stale-while-revalidate 并原子替换快照。

benchmark-ubuntu24-amd64-docker.sh 在 Ubuntu 24.04 x86_64 容器内构建当前 checkout，并把 gateway、backend、client 固定到互不重叠的 cpuset/cgroup。HTTP、HTTPS、static-large、SSE、WebSocket、TCP、UDP 与透明 QCP 按 1×/2×/4× 同时放大；逐档判定 saturation 吞吐和 equal-load p50/p95/p99。equal-load 取较慢 saturation 的 25%，双方须完成至少 98% 可执行 target。HTTP/SSE 使用 centered uniform phase 并对 aggregate slot 四舍五入；UDP/QCP 使用保留 1 ms completion guard 的同步 whole per-connection ticks，TCP 保留 2 ms，WebSocket 为 framing 和两次用户态协议转换保留 5 ms。nginx 1.31.2 mainline 使用 -O3 -fno-plt、相同 gateway cpuset、sysctl 与等价协议配置。完整矩阵 active measurement 最多 20 秒；Docker role isolation 不能冒充三台物理机。

20 秒上限按 active measurement window 累加。默认每尺度运行 1 次 saturation 和 2 次反向 candidate order 的 equal-load，共 18 秒 active measurement；latency report 使用两次样本 median。inactive gateway unpause 后双方都有相同的 1000 ms excluded settle，再安排 2000 ms future start，确保 overdue timer/I/O bookkeeping 已排空，并让 4× 下 11 个发生器完成连接池与协议预热；plain HTTP/1 建立完整连接池，HTTPS/H2 预连 multiplexed session，GET/SSE 完成两次请求，每条 WebSocket/TCP/UDP/QCP 连接完成一次 echo。预热不计入 active measurement，UDP/QCP response timeout 为 500 ms。

性能验证的数据流独立于网关：HTTP/1 发生器每个 worker 持有独立的预连接 client，HTTP/2 使用共享多路复用 client；下载逐块消费和计数，检查响应状态及夹具长度，不聚合整个大文件。共同绝对开始时间不可由迟到进程自行后移，双方任一轮未完成等负载目标都会失败；CDN 发布预检位于测量前。完整边界与诊断方法见 验证流程。

严格矩阵中的 protocol: qcp 是透明 UDP edge forwarding：proxysss 与 nginx 等价 UDP listener 接受相同负载和门禁。该结果不代表 proxysss 在热路径解析或终止 QCP frame；KCP 专用封装仍不进入默认 nginx head-to-head 矩阵。

CDN 回源与安全目录服务

services.static_sites 支持回源令牌、TCP 对端 CIDR、短期 HMAC-SHA256 签名 URL、站点限流和缓存控制。鉴权先于文件缓存、HEAD、Range 与 304；签名资源返回 no-store。目录索引默认关闭，显式开启后支持大小、GMT 时间、安全链接和条目上限；默认隐藏点文件并检查真实路径边界。

源站令牌只鉴别 CDN，访客防盗刷和缓存命中时的授权须在 CDN 边缘执行。阅读完整配置、签名算法与幂等验证说明 →

请求链：当前配置 → 对端 ACL/限流 → 回源令牌与签名 → 路径/符号链接边界 → index/目录索引 → 条件请求/Range → 有界缓存或流式文件。热重载重新预热并清理静态路由映射；可变配置不复用连接上的免策略静态快路径。不可变无策略 H2 热静态路由保留连接 OnceLock 与 ArcSwap payload。

安全开关与 Windows/macOS/Linux 适配

proxysss config security 输出安全开关、默认值和中文建议；CDN 鉴权与 FTP 策略可独立停用，保留规则。proxysss config performance 只读探测系统版本、I/O 后端和 socket 参数。Windows/macOS 保留 TCP 自动调节，并提供 keepalive、有界 UDP 缓冲；Linux 延续发行版与 CPU 自适应策略。Windows/macOS 保持现有调度，系统适配只作用于 socket；Linux 保留 CPU 自适应数据运行时。runtime.performance 在启动时固定，修改后需重启。

Docker 验证固定使用 proxysss-verify，运行前后清理同名项目容器，报告覆盖写入项目内固定目录。查看完整配置、安全建议和验证边界

管理后台与内置文档

默认在 http://127.0.0.1:7777/ 查看运行状态。后台使用中文导航、表格与表单，原始 JSON 位于可折叠的诊断区。配置写入和配置展示默认关闭。管理监听器与公共监听器均提供 /docs.html；文档模板、样式和交互脚本嵌入单个二进制。

Windows 使用隐藏启动器注册登录自启动。英文与中文安装说明分别位于仓库的 README.md 和 README-CN.md；详细配置见配置指南。

热正文缓存持有自有不可变 Bytes 快照，单对象读取最多 32 MiB，不直接 mmap 可变文件；源文件截断不会让 TLS/压缩访问失效映射。2 秒 freshness 与后台刷新期间可继续发送旧快照，H2 删除/重验证失败会使连接快照失效并回到正常分发。资源发布仍推荐原子替换。

正文缓存使用原子预留的 256 MiB 上限；进程内全部静态快照（含正在填充、已淘汰但响应仍引用的正文）另受 320 MiB 硬上限约束。最后一个 Bytes 引用释放时归还预算，预算耗尽的冷下载立即回退流式读取，预热跳过该对象。缓存淘汰只扣减一次，填充协调锁随成功、失败或取消清理；缓存命中不重新争用预算。此上限不包括 socket、TLS、压缩输出与其他网关内存。

游戏资源与复杂下载

原生静态服务支持单段和最多 16 段 Range，合并重叠区间并流式发送 multipart/byteranges。HEAD 忽略 Range；条件失败返回 412，全部越界返回 416。大文件局部读取不载入整文件，取消释放资源。脚本 API 无需变化。

SSE 消息边界与资源释放

src/http1_body.rs 在原始 SSE 转换为 TLS/HTTP2 响应前按 HTTP/1 消息边界解码：chunked 去除大小行、扩展与终止分隔符，消费并丢弃 trailer；Content-Length 精确计数，无长度响应才以 EOF 结束。大小/元数据行最多 16 KiB，trailer 总量最多 64 KiB。长度冲突、未支持的 transfer coding、分块错误或正文提前 EOF 会终止响应。

每次仍按下游需求借用池缓冲并返回 Bytes 切片，不积累完整 chunk 或 SSE 事件；完成或取消释放上游。SSE 不再压缩，但保留上游已有 Content-Encoding，避免移除编码头后让客户端误读压缩字节。配置与使用边界

静态站点与缓存所有权

按 hosts/path 首个匹配项选站后执行授权。多站点或配置 hosts 时，预热路由键由站点序号与路径组成；H2 快照和连接缓存使用相同键，避免同路径覆盖。单个无 hosts 站点继续借用路径作为键。正文按真实文件路径共享有界快照，但站点授权、响应头与条件处理独立执行。重载清空路由/H2 映射后重新预热；可变配置不使用连接级免策略缓存。

流式协议与入站正文边界

HTTP/1 原始上游响应共享分帧校验：拒绝冲突 Content-Length、TE/CL 共存和不支持的 Transfer-Encoding；跳过有界信息响应后转发最终响应。chunked 先校验再发送有效前缀，不混入尾随响应。固定长度或 chunked 提前 EOF 作为失败关闭，异常连接不能回池。

上游等待分为连接、响应头期限与逐帧正文空闲期限，持续 SSE、下载不受总时长限制，下游背压不消耗上游空闲预算；WebSocket 非 101 响应仍完整转发正文。HTTP/2 快速路径仅处理已结束的入站正文，不凭 GET 或缺少 Content-Length 推断无正文。

HTTP/3 每个请求流独立驱动，慢上传/下载不串行阻塞其他请求；发送保持 QUIC 背压并保留 trailers，正文生产失败重置流，不发送正常 FIN。访问日志和错误装饰与其他 HTTP 路径一致。入站正文受单请求大小和空闲期限限制，失败不分发；当前仍按请求缓冲，不宣称大上传零拷贝。配置和限制。

原生 reactor 的事件与接收边界

TCP/WebSocket 与 sendfile owner 先消费完整个 epoll_wait 事件批次，再安装新连接或下载，避免旧 ERR/HUP 作用于复用 fd 的新任务。每轮最多接收 256 个任务，剩余队列通过 eventfd 唤醒下一轮，让已有流量先处理 I/O；不减少 CPU 自适应 owner 数，也不改变数据发送预算和背压。

EPOLL_CTL_DEL 不会删除已取回用户态的事件，参见 Linux epoll 事件缓存说明。

原始 HTTP 上游空闲池记录 socket 的 runtime ID。同 runtime 直接复用；控制面预热转入数据面或跨 HTTP shard 复用时，解除旧 reactor 注册，通过非阻塞 peek 排除关闭或有残留数据的连接，再把同一 TCP 连接注册到当前 reactor。池容量不变、不额外预拨，也不把普通转发改成重连。

UDP 会话替换与清理

UDP 清理在同一分片操作内核对 association 的 Arc 身份，旧 reader、发送失败或容量清理不能误删同地址的新会话。替换会话会停用旧实例；reader 检查自身活跃状态和 TTL，观察到停用后退出并停止转发迟到回复，不借用新实例的活跃时间维持旧 socket。本地缓存判定过期前读取共享刷新时间，避免其他 worker 的活跃会话被旧缓存关闭；容量候选已刷新或替换时跳过本次淘汰。

低频 HTTP/1 静态连接的时效

明文 HTTP/1 连接缓存每次命中都检查单调时间上的 2 秒 freshness，不按请求次数推迟检查。低频复用同一连接仍会触发共享后台重验证，不能因尚未积累 256 次访问而长期保留旧版本；过期不等于每次同步 stat，文件刷新仍由现有控制运行时合并执行。
